# 面向问题的网络观测策略

状态：Draft（研究结论与实施建议，含0.7.0进展）；2026-10-23；维护：项目维护者。[当前架构](ARCHITECTURE.md)描述已实现内容，[文档导航](../README.md)提供规范入口。

当前增量：已接入用户确认的HTTPS代理只读API，只调用GET /version与/connections，保留有界连接快照并提供脱敏导出；受控测试不等于真实代理API验收，后者尚未完成。报告已增加最小来源外层`evidenceEnvelope`，并明确跨来源关联未建立；完整事件契约、关联器与下述自适应规划仍是目标设计。

## 需求优先级

| 用户问题 | 需要区分的解释 | 最先取得的信息 | 下一条有价值的证据 |
|---|---|---|---|
| 网站打不开/很慢 | 解析、连接/代理隧道、TLS、HTTP策略、正文等待 | 当前网站事件、系统配置、同计划有限复核 | 对应失败层的受控正/负例；核心同窗记录 |
| 代理已开却像没代理 | 分应用、显式HTTP、VPN标签、规则直连、代理入口失效 | 用户声明与本次proxy/socket观测分别记录 | 核心连接/命中规则与独立端点的可解释关联 |
| DNS是否泄露 | 系统解析、代理代解析、fake-IP、引导解析、允许的直连 | 当前解析配置与同域同类型查询 | 带nonce的受控权威/解析器记录，加覆盖明确的出口观察 |
| 配置修复是否生效 | 文件已保存、客户端未加载、覆盖规则、间歇故障 | 原计划、修改差异、读回回执 | 客户端加载证据与同计划复测，必要时受控A/B |
| 某个其他App绕过代理 | 未纳入VPN、主动绑定、其他资料、系统流量 | 当前模式与明确目标应用/任务 | 有采集覆盖与UID依据的设备/外部后端 |

前三项属于近期核心需求。跨应用归属、全设备数据包、QUIC与受控解密是增强需求。无法在当前普通权限下观察的内容必须给出具体缺口和可选实验，不能只显示无行动意义的“未知”。

## 采用能力组合而非权限等级

基础组合：Android公开信息＋本应用探针＋本机实验。代理协同组合：在基础上接入用户指定的代理只读证据。深度组合：按问题单独接入ADB、网关、受控服务或经授权的系统捕获。每个后端都可以缺失，拒绝其中一个不应阻止基础诊断。

这些组合不是必须固定成四个导航标签。界面围绕“网站异常 / 代理是否处理 / DNS路径 / 修复复测”选择任务，再展示所需能力；专家可查看完整计划。沿用Material3三入口，默认一次确认目标与预算；增加采集点或改变被测环境需要显示实际变化。

选择标准依次是：是否能区分当前假设、覆盖与关联是否可靠、对被测网络的干扰、敏感数据范围、功耗与部署成本。仅权限更低但会改变路径的方案未必优于授权明确的外部观测。

## 自适应实验规划（目标设计，当前未实现）

采用可审计规则和有限假设集合，不要求大模型、上传报告或虚构概率。每个候选实验必须包含：要区分的假设、前提、预期结果、反例、所需能力、目标/预算/副作用、停止与降级。

示例：网站TLS失败。

1. 保留连接成功、证书/身份/协商的具体错误，以及设备时间观察。
2. 若是证书时间或信任错误，检查该证据对应的时间/证书条件；不先改DNS，不用重试抹去首次失败。
3. 若是握手等待而没有证书错误，可用同计划有限复核、受控可信TLS正例和代理连接快照区分“持续性路径问题/暂时等待/工具本机异常”。更换目标是新实验，不冒充原目标已修好。
4. 只有相应后端能提供独立信息时才建议升级。无可信控制端点时保留候选解释，提供明确操作；不扫描本机端口或强行启用VPN捕获。
5. 已有证据足以定位处理范围、剩余预算不足、用户取消或网络条件变化时停止；输出“已排除/仍可能/下一最小实验”的依据。

DNS示例：NOERROR空AAAA或fake-IP特征地址先结合记录类型、同域UDP/TCP和代理DNS模式解释。权威日志中的递归器来源不能直接证明手机第一跳；缺失日志也可能是缓存/采样/覆盖问题。升级抓包前必须明确会观察哪个接口、是否能看到蜂窝和IPv6以及是否改变原代理。

## 推荐推进顺序

1. 修复现有元数据与文档所列实现欠账；保留已有协议语义、原始报告和冻结发布物。
2. 用兼容外层统一现有两种报告的来源、时间、完整性，先打通一次诊断到复测的纵向流程。
3. 有界代理协同读取已接入；继续验证真实端点/字段兼容和受控关联实验，取得关联依据后再提供本应用规则/节点解释。
4. 再增加受控DNS权威/网关证据、地址族与协议专项。需要其他应用时才研究独立VPN/Root后端。
