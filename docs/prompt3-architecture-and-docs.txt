任务：基于现有 Android 代理诊断工程，完成有证据的架构研究和可回溯的文档治理
版本：2026-10-23；本文件整合 prompt1.txt 和 prompt2.txt，保留两份原文作为输入。

一、任务范围与完成定义
在当前工作区实际执行，不停留在建议。顺序为：核实现状 → 研究用户任务与证据缺口 → 比较方案 → 形成架构决策和数据契约草案 → 整理文档 → 自动验证并报告。
本轮修改文档与文档检查工具；不改变 App 业务实现、权限、依赖、版本或安装包。架构研究中的“建议下一步实现”不自动等于本轮实现授权。不得为了使文档正确而偷偷改代码。
用户任务优先：网站分层故障定位、代理协同核验、DNS 路径与泄露验证、配置生效与修复复测、必要时其他应用或全设备观测。
完成需有新 prompt、现状清单、能力比较、决策记录、事件契约草案、实验矩阵、实际迁移和机器验证结果。

二、先调查与保留
1. 确认项目根目录、AGENTS、Git 状态与正在进行的工作。没有 Git 时不得假装能用 git diff 回滚：先保存维护文档原件、路径映射与 SHA-256，再移动文件。
2. 枚举作者维护的 Markdown/TXT、引用附件、脚本路径与文档入口；检查隐藏配置，但排除生成缓存、构建产物与第三方内容的重复审计。
3. 原用户报告、真机原始数据、历史 verification、dist 中已发布文件、SOURCE-SHA256SUMS.txt、许可证及第三方通知保留。完整手机报告不得复制进源码交付目录。
4. 保存业务源码、构建配置、历史证据和输入 prompt 的摘要，结束时复核未改变。
5. 不擅自启用 Root、第二个 VPN、CA 安装、代理写接口或设备配置变更；研究权限不等于使用权限。本轮不进行新的手机实验，也继续不运行模拟器。

三、按问题与证据缺口选能力
对每项能力使用：用户问题 → 可证伪假设 → 需要的事实 → 候选采集点 → 权限/凭据 → 覆盖与干扰 → 验证方法。
不以“字段越多越好”作为验收；不以“低权限”直接推出低干扰。仅当新证据能够区分当前竞争解释时，才建议增加采集成本或权限。
比较普通 Android API/主动探针、代理只读 API、独立 VPN/TUN、ADB 主机协作、Root 采集、网关/受控端点等方案。模式由场景组合，避免为每种权限重复造一套引擎。
区分权限获批、接口可调用、流量经过采集点、信息可解密、归属可证明；分别记录未知、拒绝、不可用、不支持、丢失与解析失败。
依据优先级：当前源码和保留实测 → 官方平台/代理源码与文档 → 明确标注的设计推断。对 API、版本和接口约束查官方资料，记录链接、核查日期和本地快照路径/版本；不要把官方文档支持写成当前设备实测。

四、架构研究具体产物
1. 当前实现与目标能力对照：核对新旧诊断链、报告模型、元数据、修复闭环、权限及数据存储。发现业务缺陷只记录，不越界修复。
2. 能力矩阵覆盖：用户目标、数据来源/位置、授权类型、Android/厂商条件、代理共存与扰动、流量范围/盲区、UID归属、协议/明文深度、降级、功耗/隐私、证据等级与验证状态。
3. 决策记录：问题、候选、选择依据、取舍、状态、未决风险和重新评估条件。既有已确认决定与本轮新建议分开。
4. 模块与契约草案：能力协商、计划/尝试、观测事件、来源/版本、时间与时钟误差、关联依据、完整性/丢失、推断与修复回执。不要把草案宣称为现有 JSON schema。
5. 关联必须可解释：显式请求标识优先；连接元组加时间与采集边界只能按条件关联；相同 IP 或近似时间不能独立确定同一请求。保留原始事实、解析派生与假设的关系。
6. 自适应实验作为目标设计：每次候选实验说明区分哪些假设、预计证据、预算/副作用、停止条件、后端不可用时的替代；先用可审计规则，不引入无依据的数字置信度或大模型依赖。
7. 实验矩阵：直连/代理/TUN/规则直连与代理/系统与代理DNS/IPv4与IPv6/UDP与TCP/TLS负例/HTTP错误/换网/多源关联/受控解密。每项记录预期、参考答案、实际证据、误判风险和验收；本轮未执行的明确写计划，不能靠复制旧结果填通过。
8. 下一最小实现必须是端到端纵向流程，含失败、拒绝授权、后端缺失、错误关联和恢复验证；给出依赖与验收，不泛列功能。

五、文档治理与迁移
1. 每个现有文档建立原路径、标题/主题、读者、类型、范围、引用、独有价值、冲突、状态、操作/目标、依据及风险。许可证、冻结证据、生成清单单独分类。
2. 当前规范、当前实现说明、操作指南、历史报告、研究草案分开。每个主题只有一个权威入口；草案不得覆盖已确认需求，历史实测不得被新状态改写。
3. 目录保持浅层且有内容，尊重现有有意义命名。不机械套模板、不为减少数量丢知识。重叠通过职责划分和链接处理；不确定项保留并登记。
4. 执行实际移动/必要改名与引用重算；迁移前校验绝对路径在工程内，拒绝覆盖目标。对已对外引用的旧路径保留明确的兼容跳转页，跳转不是第二份规范。
5. docs/README.md 为唯一完整导航；根 README 简明，START-HERE 为阅读路线。建立轻量元数据、状态转换、代码变更对应文档更新规则和维护检查。
6. 对当前文档修正已核实过时信息，历史版本保留当时范围；后续真机结果以独立追加摘要引用，不能把发布前“未测”改成当时已测。
7. 未解决问题区分可实施欠账、需要实验、需要用户策略选择，不把所有问题都称作阻塞。

六、验证与交付
增加无外部依赖的文档检查工具并自测：本地 Markdown 文件/附件链接、相对基准、URL编码、精确大小写、支持的标题锚点、索引可达性、迁移目标。
正常导航循环允许；“无坏链接”不等于语义正确，另人工核对权威性、现状/计划、测试时间与覆盖范围。说明检查器支持范围，远程链接访问验证和本地静态检查分开。
复核源码/构建/冻结发布/原始证据/输入 prompt 摘要；记录所有迁移、新文件、兼容入口与内容变更。SOURCE-SHA256SUMS 是历史包清单，不为新工作树重写。
产出治理规则、机器清单、问题账本、迁移报告和验证 JSON。无 Git 时明确提供备份位置与审计映射，不能宣称干净工作区或提交已完成。
最终回答给出新版 prompt、文档总入口、架构结论、实际迁移数量、验证结果和真实剩余事项。不得只输出计划，不要求用户逐阶段确认。
