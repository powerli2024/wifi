# 任务：一次性完成项目文档治理、结构重构与迁移验证

## 0. 你的角色与任务目标

你是一名资深软件架构师、技术文档治理负责人和代码仓库维护者。

请直接操作当前工作区中的项目，对现有文档体系进行完整治理。本任务不是单纯提出建议或生成一份整理计划，而是要求你在当前对话的一轮执行中，完成文档结构规范设计、现有文档审计、文件分类、必要的重命名与移动、索引重建、引用修复以及最终验证。

目标是建立一套长期可维护的文档体系，使开发者能够迅速回答：

1. 第一次了解项目应该阅读什么？
2. 当前产品需求、架构和技术规范分别以哪份文档为准？
3. 某个功能的设计、实现、测试与验收证据在哪里？
4. 哪些文档是当前规范，哪些是操作指南，哪些是历史记录？
5. 修改代码后需要更新哪些文档？
6. 如何避免重复文档、过期说明和互相矛盾的设计？

必须基于仓库实际内容工作。不要仅凭文件名判断文档职责，不要将示例目录结构机械套用到项目。

## 1. 执行原则

### 1.1 一轮完成实际工作

在当前任务中完成所有可以安全完成的操作，不要只输出计划，不要每完成一个阶段就暂停等待确认。

如果某个局部问题无法可靠判断，应保留原文件，记录待决事项，并继续完成其他不受影响的任务。

除非遇到无法安全绕过的硬性阻碍，不要因为存在少量不确定事项而放弃整体任务。

### 1.2 先调查，后修改

开始前：

- 确认仓库根目录和当前工作区。
- 检查 Git 状态、当前分支、未提交修改及是否存在进行中的工作。
- 枚举全部文档，包括 Markdown、TXT、文档中的附件引用，以及其他具有文档性质的文件。
- 检查根目录、`docs/`、隐藏目录、子模块及与文档有关的配置。
- 阅读关键文档的实际内容，而不是仅依赖文件名和修改时间。
- 搜索文档之间的相互引用、代码中的文档路径引用、CI 配置、脚本及项目入口引用。

如果仓库有未提交修改，不要覆盖、丢弃或重置这些修改。不要假设所有现存文件都由你创建。

### 1.3 保护项目完整性

禁止：

- 删除仍有价值的历史记录或技术证据。
- 擅自修改代码实现以迁就文档。
- 把设计目标改写为已经实现的功能。
- 把尚未执行的测试写成通过。
- 把最新修改的文档自动认定为权威规范。
- 为了减少文件数量而将职责不同的文档强行合并。
- 将不确定的重复文件直接删除。
- 改写许可证、版权声明、安全政策或第三方来源信息而不核实其影响。
- 覆盖用户已有的未提交工作。

优先使用可追踪的移动和重命名操作，保留必要的历史记录，并确保迁移过程可审查。

## 2. 阶段一：建立文档清单与现状审计

为每个文档建立记录，至少包括：

- 原始路径。
- 文档标题和实际主题。
- 文档类型。
- 主要读者及用途。
- 描述的功能或模块。
- 与其他文档的依赖和引用关系。
- 是否包含独立、有价值的技术信息。
- 是否与其他文档重复或冲突。
- 当前有效性：当前规范、当前指南、历史记录、待验证或未知。
- 建议操作：保留、移动、改名、合并、拆分、归档或进一步调查。
- 建议目标路径。
- 判断依据和风险。

重点识别以下问题：

1. 同一主题存在多个相互竞争的规范。
2. 版本评审和测试指南混杂在当前设计文档中。
3. 架构、产品需求、功能规范和实现细节边界不清。
4. 文档名称无法准确反映实际内容。
5. 文档内容重复、过期或互相矛盾。
6. 存在孤立文档、失效链接和缺失入口。
7. 文档描述与实际代码、测试结果或项目状态不一致。

审计结果应形成可供后续维护的文档清单和问题列表，而不是只在最终回答中口头概括。

## 3. 阶段二：设计适合本项目的文档治理规范

根据审计结果，设计并实施适合当前项目规模的文档管理结构。

可以参考以下逻辑，但不得将它视为强制目录模板：

- 产品定义：目标、用户场景、需求、功能边界。
- 架构设计：系统结构、模块职责、数据流、设计决策。
- 技术规范：功能协议、接口契约、核心工作流。
- 测试与验证：测试策略、测试指南、覆盖范围、验收标准。
- 版本与发布：版本评审、发布说明、构建报告。
- 参考资料：外部来源、技术依据、许可证。
- 历史归档：已经被替代但仍具有追溯价值的材料。

目录应尽量浅、职责清楚、适合日常开发。不要为了形式完整而创建大量空目录。

制定并落地以下治理规则：

### 3.1 权威文档规则

为每个主要主题确定唯一的权威规范。

其他文档应通过链接引用权威规范，而不是复制一份长期独立维护的内容。

如果现有文档之间存在冲突，应根据内容、实现、测试证据和明确的项目决策进行判断。无法确认时，保留差异并标记待决，不得自行编造最终结论。

### 3.2 文档类型规则

明确区分：

- 规范：系统应该满足什么要求。
- 架构设计：系统为何如此设计。
- 操作指南：如何完成具体操作。
- 测试报告：某次测试实际观察到什么。
- 版本评审：某个版本发现了什么问题、作出了什么决定。
- 参考资料：外部依据、原始来源和许可证信息。

同一文档可以包含多种内容，但应有明确的主要职责。

### 3.3 生命周期规则

定义文档的有效状态，例如：

- Draft：草稿。
- Active：当前有效。
- Superseded：已被替代。
- Archived：历史归档。
- Unverified：尚未验证。

这些状态不应只是装饰性标签。应说明各状态的含义、转换条件和维护要求。

对于版本专属材料，明确对应版本、适用范围及其是否仍然有效。

### 3.4 命名与元数据规则

制定一致的文件命名约定，优先使用清楚、稳定、易搜索的名称。

是否使用全大写、连字符、版本前缀等形式，应根据项目现状决定，不要为了统一大小写而进行无意义的大规模重命名。

对于长期维护的关键文档，按需增加简洁的元数据，例如标题、状态、适用版本、负责人或维护角色、最后验证依据，以及权威文档链接。

避免为了元数据而引入繁琐的维护负担。

### 3.5 维护规则

明确何时必须同步更新文档，例如：

- 修改公开接口或模块契约。
- 改变架构或数据流。
- 新增用户可见功能或权限需求。
- 修改测试流程、验收标准或兼容性声明。
- 发布新版本或改变已知限制。

规定文档必须反映已验证事实，并明确如何检查过期文档、失效链接及重复规范。

## 4. 阶段三：实际分类、移动、改名与内容整理

依据已建立的治理规范，对现有文档逐一处理。

### 4.1 文件分类

将文档移动至合理位置。保持必要的逻辑关联，并优先考虑开发者的检索效率。

不要只根据前缀分类。例如，`V0.6-TEST-GUIDE.md` 可能是通用测试指南，也可能是特定版本的验收记录，必须检查实际内容后再决定归属。

### 4.2 文件改名

对名称含糊、重复或不符合最终命名规范的文件进行改名。

名称应反映稳定的主题或用途，而不是临时任务过程。

避免为了追求一致而重命名本来清晰、被大量外部引用或受到工具约束的文件。

### 4.3 内容去重与整合

对于重复文档：

1. 比较实际内容，而不是只比较标题。
2. 判断是完全重复、部分重叠、历史差异还是不同职责。
3. 确定唯一权威来源。
4. 将有价值的独立信息迁移到合理位置。
5. 在旧文档保留必要的替代说明、链接或历史记录。
6. 只有在确认没有丢失重要信息且引用已处理后，才删除确实多余的副本。

如果某份历史文档包含独有的决策背景、测试证据或版本问题，即使内容已经过期，也应优先归档，而不是删除。

### 4.4 修复文档内容

修复明显的路径、目录名称、版本号和交叉引用错误。

对于架构、功能和兼容性陈述，必须依据源码、测试证据或可信的项目记录判断。

不确定的技术事实应标注为待验证，不能通过润色语言制造确定性。

## 5. 阶段四：建立统一入口与文档导航

建立或重写 `docs/README.md`，作为文档体系的主要入口。

它至少应包含：

1. 项目文档的总体结构。
2. 第一次阅读项目时的推荐顺序。
3. 当前产品规范、架构规范和关键技术契约的链接。
4. 功能开发、测试验证和故障排查的入口。
5. 版本记录与历史归档的入口。
6. 各文档的职责说明。
7. 文档状态及权威性说明。
8. 文档如何更新、如何验证、如何归档。

根据项目实际需要，可保留一个精简的根目录 `README.md` 作为项目总入口，并从那里链接到文档导航。

不要让根目录、`docs/README.md` 和其他索引各自复制一份不断分叉的文档清单。

## 6. 阶段五：链接修复与一致性验证

完成所有迁移后，必须进行实际检查。

### 6.1 路径与引用

- 搜索仓库内所有指向已移动文件的 Markdown 链接。
- 搜索代码、脚本、CI 配置及其他文档中的旧路径。
- 修复所有可以确定的失效引用。
- 检查大小写敏感环境下的路径正确性。
- 检查相对链接的解析基准是否正确。
- 检查文档入口是否存在循环引用或不可达页面。

不要只依赖人工抽查。

### 6.2 内容一致性

- 检查是否仍存在多个互相竞争的权威规范。
- 检查当前规范是否引用了已经归档的文档作为唯一操作依据。
- 检查版本专属指南是否被误认为当前通用规范。
- 检查文档是否声称实现了尚未实现的功能。
- 检查所有标记为已验证的关键结论是否具有相应依据。

### 6.3 自动化检查

如果项目已有 Markdown lint、链接检查或文档测试工具，应沿用现有机制。

如果没有，可以增加轻量级检查脚本或说明，但不要为了文档整理引入庞大的新依赖。

至少验证：

- 所有本地 Markdown 文件链接均可解析，或被明确记录为外部、动态及例外链接。
- 所有文档索引指向真实存在的文件。
- 所有移动和重命名均有对应的结果记录。
- 新的治理规范具有明确入口。
- 没有意外修改代码、构建配置或运行时行为。

如果某项检查无法运行，明确记录原因，不得将其报告为通过。

## 7. 阶段六：形成治理结果和后续维护依据

在新的文档结构中保留简洁、可维护的治理说明，并生成本次迁移报告。

迁移报告应包含：

### A. 最终结构

展示实际完成的目录树，并解释关键目录的职责。

### B. 文件迁移清单

逐项列出：

- 原路径。
- 新路径。
- 操作类型。
- 处理理由。
- 重要内容是否迁移。
- 是否需要后续人工决策。

### C. 治理规则

记录权威文档规则、命名规则、生命周期、更新流程及归档条件。

### D. 重复与冲突处理

列出发现的重复内容、冲突规范、最终采用的依据，以及无法消除的分歧。

### E. 验证报告

记录执行过的检查、实际结果、未通过项及尚未执行的验证。

### F. 未完成事项

仅列出确实无法安全完成或需要项目负责人作出决定的事项，并说明为什么不能直接处理。

## 8. 执行与交付要求

请在当前工作区直接完成任务。

推荐执行顺序：

1. 检查工作区和 Git 状态。
2. 审计全部文档。
3. 确定并记录治理规则。
4. 生成迁移映射。
5. 实施文件分类、移动、改名和内容整合。
6. 更新文档索引与交叉引用。
7. 执行自动化检查和一致性验证。
8. 输出最终迁移报告。

以上是同一任务中的连续步骤，不应在每一步完成后等待用户确认。

对于低风险、证据充分的修改，直接执行。对于高风险或依据不足的操作，选择可逆方案并保留原始材料。

完成后，给出：

- 文档治理结构的简要说明。
- 关键权威文档的最终位置。
- 主要迁移结果。
- 验证结果。
- 仍然存在的风险和待决事项。
- 当前 Git 工作区的变更概况。

不要只回答“已完成”，也不要只给出建议而不实际修改文件。

**最终成功标准：文档体系不但更整洁，而且权威来源清楚、历史信息可追溯、引用有效、维护规则明确，并且没有因整理而丢失项目知识或破坏现有工作。**
