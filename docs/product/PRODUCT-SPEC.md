## 1. 先修正产品目标

产品定位：**帮助用户解释手机代理环境中的网络现象，收集可追溯证据，并完成可复核、可恢复的设置调整。** 面向普通用户提供少输入的入口，面向专业用户保留目标、方法、条件、原始结果及局限。专业性体现在结论可靠和操作可解释，不等于首页放满参数。

| 原始要求 | 需要纠正的风险 | 建议写入需求的目标 |
|---|---|---|
| 尽可能全面地获取信息 | 多探针可能共用一个解析器或 VPN，重复信息不等于独立证据；探测还可能改变被测环境 | 建立能力目录，按问题选择最小必要的证据组合；显示覆盖和盲区，再允许用户扩展 |
| 处理冲突 | 系统 DNS、raw A、代理 fake-ip、不同出口本来就可能不同，不能靠多数票判真假 | 先判断是否是同一待验证事实、时间窗口和目标；保留各方结果，解释差异或标记未解决 |
| 失败重试 | 重试会增加流量、延迟、缓存影响，也可能挑出一次成功掩盖故障 | 只对适合的暂时性失败做有预算的重试，保存每次尝试；换域名、目标、协议或网络属于新实验 |
| 智能修复 DNS | DNS 错误可能来自域名、API、网络或策略；更换解析器可能破坏分流、内网和防泄露策略 | 先定位问题层级，给出候选动作和理由、影响、恢复方式；低证据时先建议补测 |
| 减少输入 | 自动猜预期出口、默认信任公共服务会令判定失去意义 | 自动填可观察值和安全格式；信任、政策预期、测试范围保持明确来源 |
| Google 系列风格 | 颜色圆角的模仿无法解决流程混乱，也不能证明遵守整套规范 | 采用 Material 3 组件与系统设置式分组，统一导航、状态、字段、反馈与无障碍规范 |

不要将产品定义为“一键证明整机无泄露”或“一键修好所有代理”。目标应是回答：观察到了什么、依据是什么、还缺什么、下一步做什么、改变后能否复现。

## 2. 设计基线与信息架构

完整规范见 [交互与视觉规范](../specs/DESIGN-SYSTEM.md)。建议主目的地为 **概览 / 测试 / 修复**；结果属于一次检查的详情，从概览最近检查或运行完成进入。0.4.0 曾采用“首页 / 测试 / 结果”；0.5.0 起已迁移为当前三入口。

- 概览：一句用途、当前可观察环境、主要待处理问题/最近检查、一个主要开始动作、能力与权限摘要。被动快照变化不自动触发主动网络请求。
- 测试：先选问题场景，再展示预填计划和必要字段；初级与高级是同一流程的展开层级。运行开始后就近显示阶段、目标和取消，不能用虚构百分比表示进度。
- 修复：先选择问题或导入配置，再解释候选动作。依次展示影响预览、保存/应用、读回检查、复测与恢复；导出文件和打开设置都不是修复成功。
- 报告详情：先观察摘要和下一步，再显示探针/尝试/来源/时间/网络条件及证据局限；可导出。历史记录不是当前内存基线的同义词，持久化须另行实现。

建议使用官方 Material Components 的 Views 实现逐步迁移，保持现有 Kotlin 核心与控制器；不为外观重写整个网络层或强制改用 Compose。0.5.0 锁定 Material Components 1.13.0、采用 Material3 DayNight 主题及组件，保留现有 Views 架构。官方 Views 库已进入维护阶段，未来新能力优先 Compose；本次以渐进迁移控制范围，未宣称全面通过 Material 无障碍和设备验收。[官方说明](https://github.com/material-components/material-components-android/blob/master/docs/getting-started.md)

## 3. 功能全景与能力分层

0.7.0 的代理协同是有界快照能力：仅接受正常平台 TLS 验证的 HTTPS origin，顺序 `GET /version`、`GET /connections`，每项最多 3 秒、总预算 15 秒、响应最多 256 KiB、最多保留 100 条连接。HTTP 控制口不支持，HTTP/SOCKS 代理入口不算控制 API；不自动发现端点、后台订阅或轮询，不调用测速、写配置和断开连接接口。Secret 只用于本次请求，不进入报告或设置；界面允许查看快照标识，App 导出只提供脱敏版本。

读取成功说明用户声明的接口返回了兼容数据，不能直接证明它就是待测核心，也不能把其中连接归属于本应用。尚未实现与网站实验按请求、目标和时间的自动关联；统一证据外壳只声明来源、范围、报告身份与中止状态，不代表完整事件模型或安全结论已经落地。

以下是规划目录，不是默认全部执行的测试清单。

| 层级 | 要回答的问题 | 主要信息途径 | 默认与边界 |
|---|---|---|---|
| 环境 | 应用当前看到什么网络和配置？ | Android 默认网络回调、能力/链路快照、应用版本、Private DNS 状态、用户导入配置 | 被动优先；VPN 标签不等于请求经过 VPN，配置文件不等于已生效配置 |
| 可用性 | 哪一步不能完成？ | 系统解析、数字目标 UDP/TCP DNS、受控 HTTPS、后续协议分离测试 | 明确 DNS 解析、连接、TLS、HTTP、回显校验不同阶段；不以失败证明阻断正确 |
| 策略 | 本次请求是否满足用户预期？ | 独立提供的预期出口/解析器/允许路径，按范围执行的探针 | 未提供政策预期时仅记录，不从本次结果自动制造正确答案 |
| 配置一致性 | 系统、客户端、文件、运行状态是否一致？ | 手动选择 YAML、可选的客户端只读接口、客户端导出运行配置/日志 | 各来源记录版本与采集方式；普通 App 不能假定读取其他 App 私有目录 |
| 路径取证 | 请求实际到过哪里，有无绕过政策？ | 探针标记、受控端点/权威 DNS 日志、代理日志、网关抓包 | 需要额外环境和关联条件；不默认公网扫描、抓取其他应用或替换待测 VPN |
| 变化与修复 | 改动是否生效，故障是否复现？ | 改前基线、变更差异、配置读回、相同计划复测、多次尝试记录 | 改好一项不表示全机安全；应用/环境变化可能令前后不可比 |

执行模式：①快速检查（少字段、有界流量）②专业实验（逐协议、逐目标、明确假设）③协同取证（用户连接受控日志/网关等外部证据）。这些是能力组合，不能把专家入口变成一张需要一次填完的大表单。

详细来源和探针边界见 [信息获取、冲突与重试规范](../specs/EVIDENCE-ACQUISITION-SPEC.md)。Android 的 `ConnectivityDiagnosticsManager` 也有应用资格和权限条件，不能当作任意普通应用都能获得的诊断总线。[官方 API](https://developer.android.com/reference/android/net/ConnectivityDiagnosticsManager)

## 4. 结果、建议和动作必须分离

推荐内部数据分层：`Capability`（能否观测及原因）→ `TestPlan`（目标、范围、预算、信任来源）→ `Run/Attempt/Observation`（事实记录）→ `Finding`（解释/冲突/缺口）→ `RepairPlan`（候选变更）→ `ApplyReceipt/Verification`（应用与复验）。这是规划模型，现有 schema 2 不应被文档假装已经升级。

深度基线与专业基线分别管理。深度报告保存原完整计划到进程内，保存/替换需确认；取消、换网和缺测等不完整报告不能存作基线，确定的网络失败可以。复测使用原网址、预算、代理声明及原始 DNS 目标，输入框和当前 DNS 设置改变不静默改计划。比较先核对版本、计划和可见网络条件，再列出阶段与回答变化；同计划观察不等于修复因果成立，导出两份报告可供继续复核。进程退出后基线不恢复，当前没有持久历史库。

结果至少同时表达三件事：执行状态、观察结果、该政策是否得到证据支持。例如：UDP 请求完成 / 收到 NOERROR 地址 / DNS 真实路径仍未知。不能把三者压成一个绿灯或安全百分数。

自动建议采用可审计规则与来源说明作为第一阶段；不默认上传配置给大模型，也不生成无法解释的风险分。每条建议包含适用条件、相反证据、作用范围、风险/影响、恢复方式及所需验证。证据不足时的合法结论是“先补测”，而不是必定推荐一个 DNS 提供商。

修复四种能力明确区分：说明建议、带上下文打开设置、生成文件副本、通过已授权接口实际应用。只有第四类具备写入凭据/能力时才能称应用操作；前面三类不能自动进入“已应用”。详见 [修复工作流规范](../specs/REPAIR-WORKFLOW-SPEC.md)。

## 5. 结合这次用户试测制定首个排查流程

用户报告 `c9ece9df…` 记录系统 DNS 失败，而 UDP/TCP 均有地址，HTTPS 未测。旧版把多种系统错误折叠为 `DNS_FAILURE`；脱敏也使域名、目标、返回地址未知。不能由 1 ms 响应判断缓存、fake-ip 或真实解析器，不能把两个 `[REDACTED]` 当同一域名。

首个优先场景为“系统解析异常，原始 DNS 可响应”：

1. 保持现有代理和网络，明确系统/原始查询是否同域；记录测试计划、当前快照与范围。
2. 使用当前试用包补采有限系统 DNS 诊断码，仍保留每个原始协议结果。存在 API 错误时先看调用/网络能力，NXDOMAIN 时先核对域名，不能统一更换 DNS。
3. 若比较系统与 raw，说明系统自行选择查询地址族/缓存，raw A 不是完全相同实验。需要路径结论时增加受控日志或网关证据。
4. 有针对性的候选修改每次只应用一项，并记录原值；确认生效后用原计划复测。没有足够证据时不建议关闭安全设置。

用户可执行的填写表及限定解读见 [试测指南](../releases/0.4.0/TEST-GUIDE.md)。此方案尚未在用户设备验证。

## 6. 存储、权限和资源默认值

- 默认普通应用权限，不自动申请 root、Shizuku、ADB 授权，不开第二个 VpnService 影响被测对象；特权/网关插件为后续独立能力。
- 默认无后台轮询、遥测、配置上传、公共端点猜测。用户主动选择实验，界面在发送前明确目标、协议及预算；已核准固定计划的重试无需反复弹窗，但改变目标/范围要重新确认。
- 当前仅内存保留。计划允许保存“脱敏检查摘要和不含凭据的模板”；完整配置、IP/域名、令牌或日志的持久化必须主动选择、明确存储位置与清除方式。未决定实现前保持不落盘，不以默认同意恢复敏感配置。
- 运行槽位、并发、重试、IO、DNS/HTTP正文、配置大小均有总预算；取消后先冻结证据、清理资源，不因平台阻塞不断创建线程。计划内重试也必须包含在总截止时间内。
- 换网后当前证据失去原实验条件；不能在新网络上悄悄续跑并把两段合成一次稳定运行。具体状态/重试矩阵由分项规范约束。

## 7. 分阶段交付与验收门槛

| 阶段 | 交付范围 | 验收要点 | 明确不包含 |
|---|---|---|---|

阶段不是日期承诺。每阶段先做能证明问题的纵向流程，再扩矩阵；真实设备、真实代理配置、外部日志覆盖度都独立记录。用户当前要求跳过模拟器检查持续有效，除非后续用户改变安排。

## 8. 已确认的产品决策

用户已确认以下基线，0.5.0 按 P0 → P1/P2 推进；不自动授权后续所有特权或云端能力：

1. **交互与视觉：**采用 Material 3，逐步使用官方 Views 组件；目标导航为“概览 / 测试 / 修复”，报告作为检查详情。
2. **功能优先级：**优先把 DNS 异常的“信息获取 → 冲突解释 → 候选修复 → 应用核实 → 同计划复测”做完整，再扩更多协议。默认无 root/无接管 VPN/无云端上传。
3. **自动化边界：**允许已确认计划内的分类、有限重试；修复先给可审阅方案及恢复路径，对实际写入单独明确应用动作。默认继续不保存敏感配置，持久化另行作为可选择能力实现。
