Android 网络观测与诊断平台：架构设计原则与研究任务

一、项目目标与设计立场

设计一款面向 Android 的网络观测与诊断工具。核心目标是在尽可能不干扰现有网络环境的前提下，获取尽可能丰富、准确、可追溯的网络证据，分析设备上的网络活动、代理行为、DNS 解析、连接状态及应用层通信，并帮助用户定位异常。

工具需要兼顾两类目标：

低干扰观测： 尽可能保留 Clash/Mihomo 等现有代理的工作状态，优先使用系统公开接口、主动探测和代理客户端提供的数据。

深度观测： 在用户确有需要且环境允许时，通过 VPN/TUN、ADB、Root、系统级采集或外部抓包等方式获取更深入的流量信息。

不预设必须采用某一种技术，也不预设所有能力都应内置于 Android App。项目首先要确定用户需要解决的问题，再选择适合的技术组合。

二、核心设计原则

原则 1：根据需求提出权限，而不是根据技术方案提出权限

从用户希望完成的任务出发，推导实现任务所需的观测能力，再判断需要哪些权限和技术机制。

建议使用以下推导链：

用户目标 → 使用任务 → 所需信息 → 数据来源 → 技术能力 → 权限与授权 → 能力验证。

例如：

用户只想检测某个网站能否访问，不应因此要求全局 VPN 权限。

用户想查看 Clash/Mihomo 选择了哪个节点，应优先研究代理控制接口，而不是直接要求接管全机流量。

用户希望捕获其他应用的 IP 包，才需要比较 VPN/TUN、ADB、Root 或外部抓包等方案。

用户希望查看 HTTPS 请求内容，必须进一步分析 TLS 加密、代理解密能力、证书信任和目标应用的安全策略。不能将抓包权限等同于读取明文的能力。

每项权限都应说明：它解决什么问题、是否有更低权限的替代方案、没有该权限时会失去什么能力，以及授权后会产生什么影响。

原则 2：按照用户场景设计能力档位

不要只设计一个权限不断升级的应用，而应围绕不同用户目标设计独立、可组合的使用模式。

至少研究以下场景：

基础诊断模式

普通应用权限。

观测系统公开的网络状态。

主动执行 DNS、TCP、TLS、HTTP/HTTPS 测试。

分析延迟、响应、连接失败及网络切换。

代理协同模式

尽量不改变现有 Clash/Mihomo 的路由与转发方式。

在用户授权且接口可用时，读取代理连接、规则、节点和日志。

将代理数据与主动测试结果关联。

明确无法直接覆盖绕过代理的其他应用流量。

设备流量观测模式

研究 VPN/TUN、ADB、Root 及其他系统级采集方法。

评估不同方式对代理运行、路由、DNS、应用归属识别和电量的影响。

明确 Android 版本、设备厂商和权限方面的限制。

深度研究模式

支持与电脑、Wireshark、ADB、外部抓包设备或受控网络环境协作。

适用于需要分析完整数据包、复现异常、验证代理路径或研究协议行为的场景。

将外部工具视为可插拔的观测后端，而不是要求全部功能都由 Android App 实现。

这些模式是初步候选，而非必须照搬的最终产品结构。研究时应验证它们是否具有足够不同的用户价值，避免为了分档而重复实现功能。

原则 3：区分权限、能力和可观测性

权限获批不代表目标能力必然实现。

架构研究必须分别回答：

权限： Android 是否允许应用执行该操作？

技术能力： 当前技术方案能否采集或解析目标数据？

实际覆盖： 目标流量是否真的经过采集点？

信息深度： 获得的是连接元数据、IP 包、协议握手还是应用层明文？

结果可信度： 结论是直接观测，还是基于多个数据源推断？

例如，VPN/TUN 可以捕获经过虚拟接口的 IP 包，但不能自动解密 HTTPS；代理控制接口可以提供规则和节点信息，但不一定能看到所有直连流量；外部抓包可以观察经过网络采集点的流量，但未必知道 Android 内部的应用 UID。

所有功能说明和诊断结果都必须反映这些边界。

原则 4：最小权限不是唯一目标，还要考虑最小干扰

权限最少的方案不一定最适合所有任务，数据最完整的方案也不一定最适合日常使用。

在评估技术方案时，至少考虑：

权限范围及敏感程度。

对原有网络路径、代理和 DNS 的干扰。

数据覆盖率和信息深度。

设备兼容性与实现成本。

性能、功耗和长期运行能力。

数据安全、隐私及敏感内容保留风险。

用户理解、授权和撤销的难度。

结果是否可验证、可复现。

当用户明确需要深度捕获时，可以合理采用更高权限的方案，但必须说明其必要性、影响和替代方案。

原则 5：以能力为单位设计模块，以场景为单位组合模块

避免把基础诊断、代理控制、VPN/TUN 抓包、Root 采集和外部工具耦合在一个庞大的核心模块中。

应研究以下架构边界：

网络状态采集模块。

主动探测模块。

代理客户端适配模块。

数据包捕获模块。

应用与连接关联模块。

协议解析模块。

统一观测事件模型。

证据存储和关联模块。

诊断与异常分析模块。

权限、能力检测和模式管理模块。

模块之间通过稳定的数据契约交互，允许部分模块缺失、替换或独立升级。

不应要求所有后端都支持完全相同的数据字段。应允许能力协商，并明确记录字段不可用、权限不足、数据丢失和解析失败等状态。

三、架构决策流程

请围绕以下流程开展设计：

识别用户任务和待解决的问题。

将用户目标拆分为可验证的具体需求。

确定完成每项任务需要观察的数据。

列出可获得该数据的候选来源。

比较候选方案的覆盖率、信息深度、干扰、权限、成本和兼容性。

选择满足需求的最小权限与最小干扰方案。

对现有方案无法覆盖的能力，提供可选的增强模式。

设计授权流程、能力检测、降级策略和结果提示。

通过可重复实验验证方案，而不是仅凭 API 文档推断实际覆盖率。

根据实验结果修正架构和功能承诺。

对于关键架构决策，应保留决策记录：问题、候选方案、证据、取舍、决定、未解决风险和重新评估条件。

四、权限与能力矩阵

请为每项候选功能建立可维护的矩阵，至少包含：

用户目标与典型使用场景。

功能对应的具体数据需求。

数据来源与采集位置。

所需 Android 权限、系统授权或外部依赖。

不同 Android 版本及厂商的限制。

对 Clash/Mihomo 运行的影响。

可观测流量范围与覆盖盲区。

是否能够获取应用归属。

能否解析协议元数据及应用层内容。

不能满足目标时的替代方案。

性能、功耗、隐私和安全风险。

验证方法及测试结果。

请区分 Android 普通运行时权限、特殊系统授权、VPN 用户授权、ADB 调试授权、Root 权限，以及代理客户端自身的 API 凭据。不要把它们统称为“网络权限”。

五、诊断证据模型

设计统一的数据模型，使来自不同后端的数据能够关联，同时保留来源差异。

至少考虑以下实体：

网络环境与接口状态。

主动测试任务及其请求、响应。

DNS 查询及结果。

IP 流、TCP/UDP 连接和数据包记录。

TLS 握手与可观察的证书、协议元数据。

代理连接、规则匹配结果、代理组与节点。

应用身份及连接归属证据。

错误事件、时间线和诊断结论。

每条观测记录应包含时间戳、采集来源、采集方式、可用的关联标识、完整性状态及适当的不确定性说明。

必须区分原始事实、解析结果和推断结论。不要仅因为多个记录的目标 IP 或时间相近，就断言它们属于同一个请求。需要设计明确的关联规则，并保留关联依据和可信程度。

六、可验证的研究任务

请设计最小可行的实验矩阵，至少覆盖：

无代理时的直接连接。

Clash/Mihomo 以 VPN/TUN 模式运行。

代理客户端采用其他可行的运行方式。

代理规则命中、规则绕过和直连。

DNS 走系统解析、代理解析和其他可验证的解析路径。

TCP 连接失败、TLS 握手失败和 HTTP 层失败。

Wi-Fi 与移动网络切换。

IPv4、IPv6、UDP 和 TCP。

HTTPS 加密流量与受控的 TLS 解密实验。

不同观测后端之间的数据交叉验证。

对于每项实验，说明预期观察结果、实际记录、无法观察的内容、误判风险和通过标准。

在可控测试环境中，可以用已知的目标地址、测试域名、请求 ID、时间戳和服务端日志建立参考答案，验证工具是否真正观察到了预期流量。

不得仅以“成功抓到数据包”作为通过标准。还应验证数据是否完整、归属是否正确、代理路径判断是否有证据支持，以及采集是否改变了原始网络行为。

七、交付物与推进方式

请按以下顺序推进：

需求与场景清单： 区分核心需求、增强需求和暂不支持的目标。

技术可行性报告： 基于 Android 官方文档及相关代理项目的实际接口，验证各项能力边界。

架构比较矩阵： 比较不同采集方案，而不是预先选定某种技术。

架构决策记录： 说明为什么选择某种方案，以及放弃其他方案的原因。

模块设计与数据契约： 明确模块边界、接口和统一事件模型。

实验计划： 为关键能力制定可重复的验证方案。

最小可行版本计划： 选择能够尽快验证核心价值的最小实现。

后续扩展路线： 根据实测结果逐步引入更高权限或更深层的采集方式。

研究过程中优先使用官方文档、源码和可重复实验。对尚未验证的能力明确标注为假设，不得把理论上可行写成已经实现。

八、最终评价标准

最终架构应满足以下目标：

用户能理解每项功能为什么需要某种权限。

用户可以只启用自己需要的观测能力。

低权限模式能够独立提供有用价值。

深度观测模式能够在明确授权和限制的前提下扩展能力。

代理共存与全设备捕获之间的取舍清晰可见。

不同数据来源能够关联、交叉验证和追溯。

诊断结论具有证据支持，并明确覆盖范围与不确定性。

架构允许更换代理、采集工具、协议解析器和分析模块，而不必重写整个系统。

请先完成需求、能力和架构的分析，再提出具体技术选择。不要直接从编写代码开始，也不要为了追求全量捕获而默认要求所有用户授予最高权限。


我对这套思路的最后一个批判性补充
你的“根据需求提权限”和“根据场景提权限”，还应该补上第三个维度：根据证据质量决定是否值得升级权限。

例如，用户只想知道代理是否正常工作。基础探测和代理 API 可能已经能提供足够证据，此时启动全设备抓包不仅增加权限负担，还可能改变被测环境。

相反，如果用户正在研究某个应用为什么绕过代理，那么代理 API 的信息就不够了。这时应该明确指出当前证据不足，再推荐更深的采集方案。

因此，我建议最终遵循这条规则：

先用最低成本获取足以回答问题的证据；只有当证据缺口影响结论时，才升级观测能力。

这能让产品既有足够强的技术上限，又不至于把所有用户都变成需要配置复杂抓包环境的研究人员。
